# GDUF CS 后端工程质量优化开发方案

日期：2026-11-18（北京时间）｜版本：V1.1｜状态：待实施

修订：根据用户要求，将 Redis 从条件扩展项调整为首轮必须实施和验收的技术组件，共享缓存、登录限流、故障处理及跨进程验证全部纳入交付。

## 1. 目标与适用范围

将当前业务较完整的赛事平台，提升为业务正确性、接口契约、查询效率和生产维护都有证据支持的小型后端系统。评价标准是能否可靠交付和持续维护，而不是框架或中间件数量。

采用 FastAPI、SQLAlchemy、Alembic、PostgreSQL、Redis、Vue、Nginx 和 Docker Compose；Redis 是必要组件，必须实际接入业务、部署及 CI，不以只添加依赖或容器作为完成。保留唯一管理员、游客免登录、每届最多 32 队、三种赛制、名单版本、导入预览确认、正式赛果修正和排名快照。公开页面沿用现行视觉基准，必要的前端改动限于接口适配、分页和错误提示。

本文件只规划优化，不代表已经修改业务代码、通过验收或部署。性能、恢复时间及工期均为规划目标或估算，不是当前能力承诺。

## 2. 当前证据及问题边界

| 已有基础 | 仍需完成的工作 |
| --- | --- |
| 赛程算法、版本检查、赛事行锁、发布快照、数据库约束 | 将关键业务约束覆盖到所有写入口，并用 PostgreSQL 并发及回滚场景验收 |
| 部分 Pydantic 请求模型、公开字段白名单 | 大量裸 dict 接口、手工字段转换、输入与输出契约不统一 |
| 公开接口 2 秒进程内缓存 | 队伍/比赛 DTO 逐条查询、日期在内存过滤；缓存及限流的跨进程语义未完成 |
| 迁移、CI、容器部署、备份恢复脚本 | 生产定时备份、异地副本、监控告警和恢复演练仍需落实并留证 |
| 业务回归、浏览器流程、历史压测记录 | 当前版本完整测试未确认；原压测约 60 请求/秒，不能作为高并发证明 |

依据为当前工作区，而非仅 Git HEAD。当前存在未提交业务变更，应先建立文件清单，避免覆盖。19 号历史审查报告中的部分问题已出现修复代码及回归用例；逐项核验后更新关闭状态，不能照搬旧问题清单，也不能仅凭有修复代码就宣布关闭。

本轮评估实际完成 24 项赛制相关测试；完整测试先遇临时目录问题，调整后接口测试长时间未返回，未形成完整结果。实施时必须调查测试进程等待原因，不预先认定为应用业务缺陷或环境问题。

## 3. 技术决策

1. 采用模块化单体。按名单、赛制、成绩、排名发布、内容管理划分职责，共用一个 PostgreSQL 数据库和事务机制。
2. 路由处理鉴权、请求/响应转换；服务处理业务动作和事务内规则；查询模块负责批量取数；纯规则模块处理赛制、比分和排名计算。简单 CRUD 不强行拆出多层。
3. 保留请求结束前提交事务的语义。服务接收同一 Session，可以 flush，不能自行 commit；失败统一回滚，避免嵌套提交破坏原子性。
4. 一致性依靠 PostgreSQL 约束、事务、版本和明确锁顺序。保留赛事级串行写入这一适合单管理员的策略，测出瓶颈后再考虑缩小锁范围。
5. Redis 统一承载公开读取缓存和跨进程登录限流，替换进程内缓存及登录计数。首轮必须用两个独立 API 进程完成共享状态验收；生产进程数按资源和压测结果决定。
6. 正式数据、管理员会话、幂等凭据和审计仍保存在 PostgreSQL；Redis 不承担正式赛果的唯一存储，也不用 Redis 锁替代数据库事务。首轮不增加消息队列、微服务、搜索引擎或 Kubernetes。

建议逐步形成的目录，不要求一次性搬迁全部文件：

```text
backend/app/
  api/                 # HTTP 路由与依赖
  schemas/             # 按业务拆分请求、公开响应、管理响应
  services/            # 名单、成绩、晋级、排名发布等业务动作
  queries/             # 公开聚合、管理列表、批量取数
  domain/              # 纯赛制与比分规则
  infrastructure/      # 数据库、日志、缓存、限流
  main.py              # 应用组装
```

## 4. 工作包与实施顺序

### W0：固定版本与变更边界（最高优先级）

交付物：版本清单、路由清单、业务约束清单、迁移现状、历史问题状态表。

- 记录分支、HEAD、未提交文件和关键文件哈希；在授权开发时创建独立开发分支，完整保留用户已有修改。
- 核对模型、迁移 head、生产已知结构版本和依赖锁文件；本地安装版本与声明不一致时单独记录。选择并锁定 Redis 服务端镜像、Python 客户端版本，核对运行兼容性与许可；固定连接、内存和持久化预算。
- 列出全部写入口：后台、CLI、数据初始化、秋季赛更新脚本，以及 ORM 事件和批量 SQL；将入口对应到业务规则。
- 为每项历史问题区分“待核验、源码已修、独立验证通过、生产验证通过”，保留原始报告作为历史证据。
- 固定本轮 API 兼容边界、基准环境与最终验收数据。调查完整测试无法结束的问题列入 W6。

完成标准：每项改动均有可追溯版本；不存在把当前工作区当成干净 HEAD、把旧报告当成当前缺陷的情况。

### W1：收敛业务规则与事务（最高优先级）

主要涉及：`results.py`、`roster.py`、`tournaments.py`、`final_results.py`、`test_data.py`、`autumn_update.py`、`autumn_awards.py`、`db.py`。

先抽取以下业务动作，再让路由和脚本调用：名单修订、生成/发布赛程、确认成绩、修正成绩、确认晋级、保存排名工作稿、发布/撤回排名。服务之间调用服务，禁止调用 HTTP 路由函数来复用业务。

必须明确并落实的约束：

| 约束 | 实现要求与最终验收场景 |
| --- | --- |
| 确认后修改成绩必须走修正 | 重复确认只能返回同次操作结果或冲突；不得再次推进或覆盖下游 |
| 结果与参赛方一致 | 正式胜者必须属于双方，系列赛结果符合该赛事允许的规则；弃权/技术判负使用独立规则 |
| 过期客户端不能覆盖新数据 | 比较预期版本；同版本并发写最多一次成功，另一请求明确冲突 |
| 名单历史固定 | 所有确定参赛方的入口保存版本；已发布比赛读取时不能悄悄回退到当前名单 |
| 发布读取一致的来源 | 锁定相关记录后校验版本及指纹，生成不可变快照；并发修改时只能发布一致快照或返回冲突 |
| 来源修改使受影响排名失效 | 与成绩/晋级修改同一事务提交；失败时修改、失效、审计一起回滚 |
| 数据只关联本届赛事 | API 和数据库约束共同校验，错误关联不能入库 |
| 工作稿不能误删服务器字段 | 区分可编辑配置和服务器维护的奖励方案；明确省略、null、空列表各自含义 |

补充设计要求：

- 为确认、发布、导入等非普通覆盖写动作定义幂等语义。相同操作键+相同规范化输入返回原结果；相同键+不同输入返回 409；数据库唯一约束防止并发重复。记录保留策略必须写明，不机械地给所有接口增加操作键。
- 统一锁顺序，例如先赛事，再结果页，再各实体类别下按主键排序；审查所有路径是否相同。锁等待、死锁和超时转换为可识别的可重试错误；只有整个事务能安全重放时才做有限自动重试。
- 梳理 `before_flush` 的排名失效副作用。将失效规则抽为显式服务，覆盖 API、CLI 和脚本后再决定移除事件；迁移期间保留兼容保护，避免漏入口或重复审计。检查批量 SQL 绕过 ORM 事件的路径。
- 必要约束通过增量 Alembic 迁移增加；先查存量冲突，给出修复报告，禁止自动猜测并改写历史胜者或名单。

完成标准：约束、入口、锁顺序、失败语义均有文档；关键操作不自行提交；不能靠前端隐藏按钮保障正确性。最终由 W6 的并发、回滚和历史保护验收关闭。

### W2：统一接口契约（高优先级，依赖 W1 的业务边界）

主要涉及：`schemas.py` 及各路由，前端 API 调用层。

- 按业务拆分请求模型，优先覆盖成绩、赛制、名单、公告、直播、赞助和奖品。类型、长度、枚举、时区、集合数量有明确边界。
- 区分字段未提交、显式清空和恢复默认；更新接口只修改实际提交字段，防止默认值覆盖旧配置。
- 公共与管理员响应分别定义模型；公开响应显式过滤联系方式、SteamID、导入详情和审计资料。FastAPI 响应模型作为第二道边界，保留业务白名单。
- 统一错误结构：`error.code/message/details/request_id`。字段错误 422、认证失败 401、权限/来源失败 403、资源不存在 404、版本/状态冲突 409、限流 429；真正未知异常返回 500，并在服务端记录堆栈。
- 校验错误的 details 仅返回字段路径、错误码和可公开原因，不直接序列化包含输入值的异常对象，避免密码或报名资料通过错误响应泄露。
- 每个请求入口创建请求 ID，贯穿错误响应、响应头和日志；不再只在异常出口生成无法关联日志的随机 ID。
- 保留 `/api/v1` 已有调用兼容。队伍/赛程按一届至多 32 队保持有界全量读取；增长明显的赛事、公告、审计列表增加新分页接口，旧入口先保留并迁移调用方，禁止把现有数组直接改为分页对象。
- 导出 OpenAPI，生成或核对前端类型，记录兼容变化。将上传鉴权在解析文件前完成的现有行为纳入兼容要求。

完成标准：本轮公开与管理业务接口均有输入/输出契约；错误输入不因缺少字典键或类型转换直接变为 500；原业务浏览器流程通过。

### W3：查询与缓存优化（高优先级，依赖 W1、W2）

主要涉及：`public.py`、`results.py` 的积分查询、`final_results.py` 的列表与来源查询、`main.py` 的缓存，以及新增 Redis 客户端、缓存服务和缓存失效事件迁移。具体设计见第 6 节。

查询任务：

- 赛程批量读取比赛、队伍、指定名单快照与成员，使用映射组装 DTO；已有模型没有 relationship 时直接批量查询，不为使用某个加载 API 强改模型。
- 赛事列表的队伍数量使用分组聚合，避免逐届 count；后台统计使用数据库聚合。
- 日期参数解析为上海时区某日对应的 UTC 半开区间，在 SQL 中筛选；统一数据库时间语义和稳定排序。
- 审计列表使用稳定的游标分页；其他历史列表明确上限和分页规则，禁止无边界返回。
- 采集实际 SQL、执行次数、耗时和 `EXPLAIN (ANALYZE, BUFFERS)`。根据访问条件及数据分布决定联合索引，避免无依据地给每个字段建索引。

缓存任务：

- 使用 Redis 缓存明确允许的公开 GET 接口；规范化路径与白名单查询参数，限制键数、单响应大小和总字节数，过期后回收；不保留并行的进程内业务缓存。
- 热点回源协调使用带随机持有者标识和过期时间的 Redis 短租约，原子校验持有者后释放；租约用于减少重复查询，超时或丢失不影响业务正确性。
- 管理写入成功提交后更新共享失效代次。回源开始记录代次，回填以 Lua 原子比较代次并写入，变化时放弃旧结果。数据库事务内保存待失效事件，提交后尝试处理，失败由独立任务重试；不能声称 PostgreSQL 与 Redis 写入天然原子。
- 明确允许的最大陈旧时间。正式排名、后台和内部页面存在性检查继续遵守已有不缓存语义，避免把业务撤回隐藏起来。
- 两个 API 进程共用 Redis，核验写后缓存失效和回源协调；Redis 故障时启用有并发上限的数据库回源，防止降级流量压垮数据库。

完成标准：关闭缓存时，主要赛程列表查询数不随比赛数量逐条增长；32 队赛事的普通赛程列表 SELECT 预算先定为不超过 10 次，所有组成查询计数口径一致；超过预算需解释并复核。两个独立进程均通过缓存竞态和失效重试验收，更新代次后的旧回源不能回填；提交与失效之间的最终一致性窗口按第 6 节单独测量。

### W4：生产可观测性与基础安全维护（高优先级）

主要涉及：`main.py`、`security.py`、`db.py`、Nginx、Compose 和依赖配置。

- 输出结构化日志：请求 ID、路由模板、状态码、耗时、业务动作、异常类型。日志不记录密码、Cookie、CSRF、原始报名表或完整请求体。
- 业务审计记录操作主体（仍为唯一管理员）、动作、对象、原因、版本及必要差异；减少完整私密资料复制，定义访问与保留策略。
- 增加受控可见的请求数、错误率、延迟、数据库池使用、锁等待、缓存命中/回源指标。路由使用模板，指标标签不放比赛 ID、完整 URL、用户 IP 等无限增长字段。
- 区分存活检查和就绪检查，保留现有 `/api/v1/health` 兼容；数据库不可用时就绪检查失败，存活检查仍能表示进程状态。
- 明确数据库连接预算：进程数 ×（pool_size + max_overflow）加迁移、备份和运维预留，不超过数据库连接容量。设置连接/语句/锁等待超时。
- 维护可信代理链和登录限流隔离。登录失败计数迁移到 Redis，以 Lua 原子维护滑动窗口和 TTL；Redis 失效时新登录返回明确的 503，不退回各进程独立计数，也不绕过限流。已有 PostgreSQL 会话继续按原鉴权规则工作。
- 增加 Redis 延迟、连接数、内存、拒绝写入、缓存回源、失效事件积压和限流异常监控；清理过期会话与预览记录，任务使用宿主机 timer 或一次性 CLI，并记录失败状态。
- 检查上传大小在代理和应用侧的上限；日志滚动、存储告警和资源预算有实际配置。持续核对锁文件与公开依赖公告，按可达路径处理风险。

完成标准：一次请求可从响应 ID 定位到日志和关键动作；数据库断开、5xx 激增、磁盘不足、备份失败能够在隔离环境触发对应告警。日志和指标不得新增公开私密资料出口。

### W5：发布、备份与恢复闭环（高优先级）

主要涉及：`.github/workflows/verify.yml`、`scripts/backup.sh`、`scripts/restore.sh`、Compose、交接文档。

- 镜像按提交标识或摘要发布，记录源码版本、迁移版本、镜像、配置摘要和备份编号，避免无法重现的现场构建。
- 发布前核对迁移兼容性和备份，迁移只运行一次。新实例就绪后再切换流量；单机资源不支持双实例时，明确维护窗口和可接受中断。
- 每日数据库与媒体备份自动执行，失败告警；配置加密异地副本与保留策略，实际密钥、入口配置和证书按独立受控方式备份。
- Redis 纳入正式 Compose 和 CI 服务，配置受控凭据、健康检查、数据卷、持久化与资源限制。数据库恢复后切换缓存命名空间，隔离旧缓存；Redis 冷启动、限流状态恢复和失效事件重放均有操作步骤。
- 数据库与媒体分别备份时说明一致性窗口；需要严格一致时暂停相关写入，或采用可验证的协调方案。不能只验证数据库导入成功。
- 定期在独立空库及独立媒体目录恢复，核验计数、外键、历史名单、排名快照和图片哈希，再执行只读页面抽查。
- 兼容迁移可切回旧应用；不兼容迁移按恢复方案处理，并明确如何保留备份之后新增的数据。禁止自动清库或在未验证恢复前覆盖生产卷。

完成标准：发布记录可追溯；自动备份和异地副本存在且可用；恢复演练产出实际耗时与数据损失窗口，不能用 CI 演练替代生产备份核验。

### W6：统一审查、测试、修复与验收（最终阶段）

沿用项目既有开发约定：先完成本轮功能与改造，最后集中审查、编写/补齐测试、执行、修复和验收。前文的完成标准是最终验收条件，不表示每个开发包都穿插测试。

最终阶段依次执行：

1. 排查此前完整测试等待问题，固定独立临时目录与测试数据库；记录版本、超时、失败堆栈和进程状态，禁止无限等待。
2. 执行现有后端回归、数据迁移、前端构建、真实 API 浏览器闭环；有意义地补齐下表场景。
3. 以 PostgreSQL 和真实 Redis 执行并发、约束、回滚与共享状态验证；启动两个独立 API 进程，不能用 SQLite、内存字典或 Redis 模拟对象代替关键验收。
4. 执行查询预算、负载、缓存竞态与故障恢复验收，修复问题后重跑受影响检查。
5. 更新历史问题状态、交接文档、运行手册和优化前后对比报告。

| 类别 | 必须验证的场景 |
| --- | --- |
| 状态与历史 | 修正后重复确认；下游已完赛；名单修订不改历史；奖励方案保存保留；各种赛制的晋级版本 |
| 并发 | 两个客户端同版本保存；重复发布；发布与改分竞争；导入与名单修订竞争；同一预览重复提交 |
| 回滚 | 在修改、推进、失效、审计之间注入失败，确保整体回滚且响应不提前宣告成功 |
| 接口 | 缺字段、类型错误、边界值、显式清空、跨届引用、私密字段过滤、过期会话、来源与 CSRF |
| 缓存 | 真实 Redis 冷/热缓存、跨进程同键回源、写后失效、旧回源回填竞态、失效事件重试、随机参数容量限制 |
| 限流 | 两个进程共享滑动窗口、不同来源隔离、并发边界、成功请求精准退还本次额度、TTL 清理、Redis 故障返回 503 |
| 运维 | 数据库不可用、池耗尽/锁等待、Redis 断连/满内存/重启、进程重启、备份失败告警、空库恢复、迁移后应用启动 |

发布出口：无未关闭的核心数据一致性问题；所有必验场景通过；独立数据库测试不会访问生产；回退方式及恢复证据齐全。统计通过率不能掩盖关键业务失败。

## 5. 性能与恢复验收目标

### 5.1 固定环境与数据

以独立预发布环境执行，建议采用与正式部署同档的 2 vCPU / 2 GiB 主机、PostgreSQL 16、Redis、正式 Nginx 代理路径；若实际机器不同，单独记录，不能直接横向比较。Redis 必须计入整机资源预算，分别记录单 API 进程和双 API 进程的结果。负载发生器放在另一台机器，记录网络、磁盘、镜像和数据库配置。

数据包含：30 届合成历史赛事，每届最多 32 队，合计至少 5,000 场合法比赛；一届 32 队热点赛事；至少 10,000 条审计记录。数据由合法业务/专用生成器创建，不绕过业务限制构造“不存在的超大单届赛事”。

### 5.2 候选目标与负载模型

以下是待验证目标，W0 固定口径后执行；不保证在指定硬件上天然可达。

| 项目 | 目标与测量方式 |
| --- | --- |
| 公开热缓存混合读取 | 固定到达率 100 请求/秒，持续 15 分钟；P95 ≤ 300ms、P99 ≤ 1s |
| 禁用缓存的数据库读取 | 同数据集固定 20 请求/秒，持续 10 分钟；P95 ≤ 800ms；报告全部代表接口，不能只报平均值 |
| 合理读写混合 | 50 次公开读/秒，加每 5 秒一次合法管理动作，持续 15 分钟；无丢写、无历史漂移，读 P95 ≤ 500ms |
| 并发管理冲突 | 两个独立客户端争用同一版本；成功次数最多一次，其余返回规定冲突；审计无重复 |
| 错误统计 | 超时、连接失败、非预期 4xx/5xx 均计为错误；非预期错误率 < 0.1%，预期冲突另表列出；所有写一致性错误必须为 0 |
| 稳态资源 | 增加一次 30 分钟稳态观察；连接、缓存和内存无持续增长；CPU、内存、磁盘及连接峰值有记录 |
| Redis 必验 | 跨进程共享缓存和限流全部通过；断连时读流量有界回源、新登录返回 503；恢复后自动恢复缓存并处理失效积压，无永久旧缓存 |
| 备份恢复 | 初步 RPO ≤ 24 小时、RTO ≤ 60 分钟，以实际恢复演练计时；RPO 是可能丢失数据的时间窗口，RTO 是恢复服务耗时 |

原“100 用户+1 秒等待”脚本继续保留作为历史可比场景；固定到达率负载单列结果。报告请求发出数量、完成吞吐、超时、分接口延迟和资源曲线，避免系统变慢时请求量随之下降却被误判为通过。

日常赛事允许的丢失窗口若小于 24 小时，应提高备份频率并验证；只有实际需要更短窗口且普通备份成本不合适时，再规划 PostgreSQL 连续归档与时间点恢复。

## 6. Redis 必做设计与交付要求

### 6.1 组件职责与接入位置

Redis 首轮必须上线共享缓存及登录限流两个真实业务用途；仅拉起容器、连接 PING 或保留进程内实现不算完成。

| 能力 | 接入范围 | 主要实现 |
| --- | --- | --- |
| 共享缓存 | 赛事目录、首页聚合、队伍、赛程等允许缓存的公开读取 | 读缓存 → 未命中受控回源 → 写入短 TTL 缓存；公开排名、后台和存在性检查不进入此缓存 |
| 热点回源协调 | 同缓存键的多个 API 进程 | `SET NX PX` 短租约、随机持有者标识、比较后释放；有限等待，禁止无限轮询 |
| 登录限流 | 登录接口、可信代理解析后的来源 | Redis ZSET 滑动窗口 + Lua，沿用每来源 5 分钟最多 10 次的规则；成功只退还本次尝试 |
| 共享失效 | 所有影响公开读取的写入口 | PostgreSQL 持久化失效事件、提交后处理、Redis 随机代次切换、失败重试及积压告警 |

新增 `infrastructure/redis_client.py`、`cache.py`、`rate_limit.py`（最终位置随目录拆分确定），统一连接池、超时、脚本加载和异常分类；按同步/异步调用环境选择客户端，禁止在异步中间件里执行阻塞 Redis I/O。增加 `REDIS_URL`、命名空间、连接上限、缓存 TTL 和回源并发预算配置，敏感地址不输出日志。

### 6.2 键、生命周期与缓存一致性

- 命名空间包含环境及结构版本，例如 `gduf:prod:v1:cache:<scope>:<generation>:<query_hash>`、`gduf:prod:v1:limit:login:<source_hash>`；开发、CI 与生产绝不共用前缀。
- 缓存只保存公开 DTO；来源标识采用带秘密盐的摘要，禁止在键或日志中直接暴露联系方式、SteamID 或会话凭据。未知资源短暂负缓存，随机查询参数不产生无限新键。
- 初始公开缓存 TTL 沿用 2 秒；缓存有效期以回源开始时间为基准，慢查询不能在结束时重新获得完整 TTL。短租约、负缓存和限流键均有明确过期时间；共享代次不可随数据缓存一起被淘汰，初始化或重建使用全新随机值，防止复用旧命名空间。
- 写事务同时保存缓存失效事件；提交后立即尝试更新对应作用域代次。独立 CLI 工作进程轮询并重试未完成事件，处理可重复执行，记录重试时间与积压数量。事件表通过 Alembic 迁移创建，不依赖 Redis 消息通知作为唯一交付机制。
- 回填通过 Lua 原子比较共享代次，拒绝失效后的旧回源结果；数据库提交与 Redis 失效之间仍为最终一致性，正常失效延迟目标 ≤ 1 秒，异常时缓存寿命限制为回源开始后的 2 秒，并单独记录在途请求耗时。正式排名及需要严格读取最新状态的管理流程始终直接读取 PostgreSQL。
- PostgreSQL 是最终事实来源；结果发布、成绩确认和幂等判断不以缓存命中或短租约作为正确性依据。

### 6.3 原子限流与故障语义

- Lua 使用 Redis 服务端时间，在一个原子操作中清理过期尝试、检查数量、预留唯一尝试 ID 并设置 TTL；超过上限返回 429 和剩余等待时间。
- 验证成功时只删除本次尝试 ID，不清空整个来源窗口，避免抹掉同时发生的失败尝试。双进程按同一来源共享计数；来源之间隔离。
- Redis 超时、连接失败或内存拒绝写入时，新登录返回明确 503 和重试提示；不把依赖故障误报为密码错误，也不跳过限流。已有有效会话仍通过 PostgreSQL 鉴权。
- 公开读取在 Redis 故障时有界回源，使用短超时和熔断退避；单进程设置回源并发上限，总预算按进程数计算。超过保护容量返回明确的暂不可用响应，避免把全部请求直接转给数据库。
- 已成功提交的管理写入不能因为随后 Redis 失效失败而伪装成事务回滚；保留待处理事件并告警，按已提交结果响应。

### 6.4 部署、资源与恢复

- Redis 仅开放 Compose 内部网络，配置专用 ACL 凭据与最小命令权限、健康检查、固定镜像和客户端版本。跨主机连接需受控网络及加密传输。
- 首轮单 Redis 同时承载缓存和限流，采用 `noeviction`，防止内存淘汰静默删除限流计数。缓存必须设置短 TTL、条目/响应上限和内存准入阈值，提前停止缓存写入以保留控制状态空间；满内存按故障语义处理并告警。
- 初步 Redis `maxmemory` 预算为 128 MiB，容器限额需额外预留连接、持久化与重写开销；以实测校准，计入整机 2 GiB 预算，不能把两者设为相同值后宣称资源足够。
- 启用 AOF 并记录刷盘策略与限流状态可能的丢失窗口；Redis 不作为业务恢复的数据源。重启后先隔离旧缓存、处理失效积压，再恢复缓存读取；检测到限流状态丢失时进入不短于原限流窗口的受控新登录保护期，已有会话可继续工作。
- 部署启动核验 Redis 可连接且权限正确；运行中的 Redis 故障按前述降级处理。健康接口区分“公开读取可用”和“新登录受阻”，避免把降级误报为全部正常或让全部公开服务无条件下线。
- CI 启动 PostgreSQL、Redis 和两个独立 API 进程，执行共享限流、缓存失效、内存/断连/重启故障验证；交付监控、恢复步骤及资源成本报告。

完成标准：以上能力全部纳入 W3～W6 并通过验收。生产采用一个或多个 API 进程均不得跳过 Redis；生产增加进程前重算 PostgreSQL/Redis 连接和回源预算。

## 7. 工期、拆分与交付物

按一名熟悉项目的开发者全职投入估算，共 24～32 个工作日，已包含 Redis 实际接入、共享状态和故障验收；存量数据问题、测试等待原因和实际部署环境会影响工期。可分别交付两批，第一批聚焦正确性与契约，第二批完成 Redis、性能和运行闭环；正式发布均需经过最终验收。

| 顺序 | 工作包 | 估算 | 依赖 |
| --- | --- | --- | --- |
| 1 | W0 版本与边界 | 1 天 | 无 |
| 2 | W1 业务与事务 | 4～5 天 | W0 |
| 3 | W2 接口契约 | 3～4 天 | W1 |
| 4 | W3 查询与 Redis 共享缓存 | 5～7 天 | W1、W2 |
| 5 | W4 Redis 限流、日志、指标、维护 | 3～4 天 | W1；请求 ID 与 W2、Redis 客户端与 W3 协同 |
| 6 | W5 发布与恢复（含 Redis） | 2～3 天 | W0；最终配置依赖 W4 |
| 7 | W6 集中审查、测试、修复（含跨进程与 Redis 故障） | 6～8 天 | W1～W5 |

建议按业务动作和兼容范围形成可审查的提交：先抽取服务，再转换契约，再优化读路径，最后补齐运行配置。避免一次提交同时搬迁全部目录、变更表结构和重写前端。

最终交付至少包括：

- 业务约束与状态转换说明、事务及锁顺序说明；
- 当前 OpenAPI、公开/管理响应模型和前端兼容记录；
- 迁移清单、存量数据核验和版本化发布清单；
- 完整验收报告、并发与故障结果、性能前后对比及 SQL 查询预算；
- 监控与告警配置、备份任务、异地副本核验、恢复演练记录和运行手册。
- Redis 客户端与 Lua 脚本、键与 TTL 说明、失效事件迁移和处理任务、Compose/CI 配置、共享状态及故障验收证据。

## 8. 达到目标后的项目定位

完成本方案并取得实际验收证据后，可将项目定位为“具备赛事状态管理、事务一致性、历史快照、查询优化及运维闭环的小型生产后端”。求职展示重点是具体问题、技术决策、失败场景和量化结果。

仍不应声称已有大规模真实用户、高可用集群或超高并发经验；压测数据标注合成环境，线上经历以实际运行记录为准。

## 9. 技术依据

下列为设计参考，不是项目已达标的证明：

- [FastAPI 请求体模型](https://fastapi.tiangolo.com/tutorial/body/)与[响应模型](https://fastapi.tiangolo.com/tutorial/response-model/)：输入验证、输出转换及过滤的官方机制。
- [SQLAlchemy 性能分析](https://docs.sqlalchemy.org/en/20/faq/performance.html)：先识别 SQL、网络、取数和 ORM 组装的成本，再选择优化方式。
- [PostgreSQL 16 显式锁](https://www.postgresql.org/docs/16/explicit-locking.html)：锁行为、死锁及一致锁顺序；并发正确性应在实际数据库验证。
- [Redis Lua 脚本](https://redis.io/docs/latest/interact/programmability/eval-intro/)：原子限流与代次比较；脚本原子性不等于 PostgreSQL 与 Redis 的跨存储事务原子性。
- [Redis SET](https://redis.io/docs/latest/commands/set/)与[内存淘汰策略](https://redis.io/docs/latest/reference/eviction/)：短租约、过期及 `noeviction` 拒绝写入时的处理依据。

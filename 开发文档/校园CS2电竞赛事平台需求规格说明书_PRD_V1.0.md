# 1. 项目概述

## 1.1 项目背景

本项目旨在为学生社团举办的校内 CS2 电竞比赛提供一个统一的线上赛事平台。

目前校园电竞比赛通常需要通过 QQ
群、微信群、表格、社交媒体等多个渠道进行宣传、报名和成绩公布，容易出现信息分散、赛程不透明、比赛记录难以追踪等问题。

本项目希望通过一个独立的网站，将赛事宣传、队伍报名、队伍展示、赛程管理、比赛结果记录和直播转播整合起来。

## 1.2 产品定位

一个面向校园 CS2 电竞比赛的轻量化赛事运营与信息展示平台。

主要服务三类需求：

-   **参赛者：** 报名参赛、了解比赛规则、查看队伍及赛程。
-   **观众：** 了解赛事、观看比赛直播、查看比赛结果。
-   **赛事组织者：** 审核队伍、管理赛制、安排赛程、记录比赛成绩。

## 1.3 核心设计原则

1.  **公开透明：** 赛事信息、队伍、赛程和比赛结果对公众开放。
2.  **管理集中：** 报名审核和比赛结果由管理员统一管理。
3.  **自动化：** 比分录入后，系统自动计算胜负、积分和晋级情况。
4.  **灵活配置：** 赛事组织者可以通过后台配置赛制，而不是每次修改代码。
5.  **轻量化：** 第一版不开发不必要的复杂功能。
6.  **低成本：** 优先使用学生优惠和免费服务。
7.  **可扩展：** 数据库保留未来举办多届赛事的能力。

# 2. 项目目标与范围

## 2.1 第一阶段目标

完成一个能够正式投入校园比赛使用的完整网站。

必须打通以下闭环：

**宣传 → 队伍报名 → 管理员审核 → 队伍展示 → 赛程生成 → 比赛结果录入 →
自动更新战绩 → 公众查看结果。**

同时提供 B 站直播嵌入能力。

直播由 B 站承担，网站仅提供播放器嵌入和直播间跳转入口。

# 3. 用户角色与权限

## 3.1 游客

无需登录即可访问网站。

权限：

-   浏览赛事首页。
-   查看赛事介绍和规则。
-   查看队伍及队员公开资料。
-   查看比赛赛程。
-   查看比赛比分和历史记录。
-   查看排行榜。
-   观看 B 站嵌入直播。
-   查看公告和新闻。
-   访问报名页面。

## 3.2 参赛队伍

第一版采用公开报名表单，不要求队长注册完整账号。

权限：

-   提交队伍资料。
-   提交正式队员和替补资料。
-   提交联系方式。
-   获取报名编号和审核状态查询凭证。

队伍资料修改由管理员处理。

报名是否需要校园身份验证、邀请码或完全开放，列为待确认事项。

## 3.3 管理员

管理员必须登录后台。

权限：

-   创建和管理赛事。
-   审核报名。
-   添加、修改和管理队伍。
-   管理选手资料。
-   配置比赛赛制。
-   创建比赛阶段和分组。
-   生成和调整赛程。
-   录入比赛比分。
-   确认比赛胜负。
-   管理积分榜和晋级情况。
-   设置直播间。
-   发布公告。
-   查看操作日志。

第一版只实现统一管理员角色，后续可以增加超级管理员、赛事管理员和记录员。

# 5. 功能需求

## 5.1 赛事首页

功能要求：

-   展示赛事名称、宣传海报和介绍。
-   展示报名开始和截止时间。
-   展示赛事当前状态。
-   展示已报名队伍数量。
-   展示近期比赛安排。
-   展示近期比赛结果。
-   提供报名、赛程、战队和直播入口。
-   展示赛事公告。

赛事状态包括：

-   草稿
-   报名中
-   报名结束
-   赛程准备中
-   进行中
-   已结束
-   已归档

## 5.2 队伍报名系统

每支队伍需要填写：

  字段           要求
  -------------- ----------------
  队伍名称       必填
  队伍 Logo      可选
  队伍介绍       可选
  队长昵称       必填
  队长联系方式   必填，后台私密
  正式队员       5 人
  替补队员       最多 2 人
  Steam ID       必填
  游戏昵称       必填

报名流程：

1.  队长进入报名页面。
2.  填写队伍基本资料。
3.  填写五名正式队员。
4.  根据规则添加替补。
5.  提交报名。
6.  系统进行基础字段和重复报名校验。
7.  生成报名记录。
8.  管理员审核。
9.  审核通过后进入正式参赛队伍列表。

报名状态：

-   待审核
-   已通过
-   已拒绝
-   已撤销

业务约束：

-   一支队伍在同一届赛事中只能有一条有效报名记录。
-   同一选手不能在同一届赛事中同时加入多支有效参赛队伍。
-   每支队伍必须满足五名正式队员的要求。
-   替补人数不能超过赛事配置上限。
-   报名截止后，普通报名入口关闭。
-   管理员可以进行特殊名单调整，但必须留下操作记录。

联系方式和 Steam ID 默认不向公众公开。

## 5.3 队伍展示系统

每支通过审核的队伍自动生成详情页面。

展示内容：

-   队伍名称。
-   队伍 Logo。
-   队伍简介。
-   正式队员名单。
-   替补队员名单。
-   队伍比赛场次。
-   获胜场次。
-   失败场次。
-   胜率。
-   历史比赛记录。

队伍详情页应支持通过 URL 直接访问。

## 5.4 赛程管理系统

支持管理员创建比赛阶段。

比赛阶段包括：

-   小组赛。
-   淘汰赛。
-   决赛。
-   季军赛（可选）。

每场比赛需要记录：

-   比赛编号。
-   所属赛事。
-   所属阶段。
-   双方队伍。
-   比赛时间。
-   比赛状态。
-   比赛形式。
-   最终比分。
-   获胜队伍。
-   比赛直播或回放链接。

比赛状态：

-   待安排
-   待开始
-   进行中
-   已结束
-   已延期
-   已取消
-   判负或弃权

## 5.5 比赛结果管理

比赛结果由管理员统一录入。

支持：

-   BO1。
-   BO3。
-   BO5。

每张地图需要记录：

  字段           内容
  -------------- ----------------------
  地图名称       Mirage、Inferno 等
  A 队回合比分   数字
  B 队回合比分   数字
  地图胜者       自动判断或管理员确认
  是否加时       是 / 否
  备注           可选

系列赛结果由地图胜场数计算。

例如：

A 队 2:1 B 队。

系统自动：

1.  验证地图数量和比分。
2.  计算双方地图胜场。
3.  判断系列赛胜者。
4.  更新比赛结果。
5.  更新队伍战绩。
6.  更新小组积分。
7.  更新淘汰赛晋级关系。
8.  记录管理员操作。

特殊情况：

-   弃权。
-   技术判负。
-   比赛延期。
-   管理员修正比分。

管理员修改已确认的结果时，必须填写修改原因。

如果下游比赛尚未开始，系统可以撤销受影响的晋级结果并重新计算；如果下游比赛已经开始或结束，则必须先由管理员处理相关比赛，不能静默覆盖历史数据。

## 5.6 排行榜

小组赛积分榜展示：

-   队伍名称。
-   比赛场次。
-   获胜场次。
-   失败场次。
-   积分。
-   地图净胜差。
-   回合净胜差。
-   当前排名。

默认建议积分：

-   胜利：3 分。
-   平局：0 分。
-   失败：0 分。

由于 CS2
正常竞技地图通常通过加时等规则决出胜者，第一版默认不允许比赛平局；如采用特殊赛制，必须在赛事规则中明确。

排名规则建议默认：

1.  总积分。
2.  相互战绩。
3.  地图净胜差。
4.  回合净胜差。
5.  管理员裁定或抽签。

具体规则允许赛事管理员配置。

## 5.7 B 站直播系统

第一版不开发直播推流服务。

功能：

-   设置 B 站直播间地址。
-   展示直播状态。
-   在比赛详情页提供直播入口。
-   在直播中心展示当前直播。
-   支持比赛回放链接。
-   提供无法嵌入时的 B 站跳转入口。

技术实现优先考虑 B 站官方允许的播放器嵌入方式。

是否允许特定直播间嵌入、是否存在地区或浏览器限制，需要开发测试阶段验证。

## 5.8 公告与新闻

管理员可以：

-   发布赛事公告。
-   修改公告。
-   删除公告。
-   设置公告发布时间。

前台游客可以浏览公告。

## 5.9 管理员后台

必须实现：

-   管理员登录。
-   管理员退出。
-   仪表盘。
-   报名审核。
-   队伍管理。
-   赛事配置。
-   赛制配置。
-   赛程管理。
-   比赛结果录入。
-   直播设置。
-   公告管理。
-   操作日志。

所有管理操作必须经过后端权限验证，不能仅依赖前端隐藏按钮。

# 6. 赛事业务流程

## 6.1 赛事创建流程

1.  管理员创建赛事。
2.  填写赛事基本资料。
3.  设置报名时间。
4.  设置参赛队伍数量。
5.  设置比赛规则。
6.  设置地图池。
7.  配置赛制。
8.  保存为草稿。
9.  检查配置。
10. 发布赛事。

## 6.2 队伍报名流程

队长提交资料 → 系统校验 → 生成报名记录 → 管理员审核 →
通过后进入参赛名单。

## 6.3 比赛流程

赛事报名结束 → 管理员确认参赛队伍 → 配置分组和种子 → 生成赛程 → 发布赛程
→ 进行比赛 → 管理员录入结果 → 系统计算胜负 → 更新积分及晋级 → 决赛 →
赛事结束。

## 6.4 比赛结果修改流程

管理员申请修改 → 填写修改原因 → 系统检查后续比赛状态 →
允许修改或要求先处理后续比赛 → 更新比分及相关数据 → 记录修改日志。

# 7. 赛制与比赛规则设计

## 7.1 赛制设计原则

赛制可配置，但第一版不开发任意表达比赛规则的通用引擎。

第一版使用预设赛制模板，并允许管理员调整关键参数。

## 7.2 第一版支持的赛制

### A. 单败淘汰赛

规则：

-   每场比赛输家淘汰。
-   胜者晋级下一轮。
-   直到产生冠军。

支持：

-   16 队。
-   32 队。
-   其他人数通过预选轮或轮空处理。

非 2 的幂次方参赛数量，需要按种子排名分配轮空，或安排预选轮。

### B. 小组赛 + 单败淘汰赛

规则：

-   参赛队伍分为若干小组。
-   小组内部进行循环赛。
-   按积分和排名规则决定晋级队伍。
-   晋级队伍进入单败淘汰赛。

建议默认：

  参赛数量     分组   每组人数        晋级
  ---------- ------ ---------- -----------
  16           4 组          4   每组 2 队
  20           5 组          4   每组 2 队
  24           6 组          4   每组 2 队
  28           7 组          4   每组 2 队
  32           8 组          4   每组 2 队

当晋级人数不是 2 的幂次方时，淘汰赛通过预选轮和轮空处理。

### C. 双败淘汰赛

规则：

-   设胜者组和败者组。
-   胜者组失利后进入败者组。
-   败者组再次失利后淘汰。
-   最终产生冠军。

第一版使用标准双败模板，自动生成后由管理员确认。

## 7.3 赛制配置参数

  参数           选项
  -------------- ---------------------------
  赛制           单败 / 小组赛+单败 / 双败
  参赛数量       16～32 队
  分组数量       2～8 组
  每组人数       自动或手动
  每组晋级人数   1～4 队
  分组方式       随机 / 手动 / 种子混合
  小组赛         单循环 / 双循环
  比赛形式       BO1 / BO3 / BO5
  地图池         管理员配置
  积分规则       管理员配置
  排名规则       管理员配置
  季军赛         开启 / 关闭

赛制配置保存为结构化配置，后端负责校验参数是否合理。

## 7.4 晋级关系

比赛晋级关系独立存储。

例如：

-   来源比赛胜者进入目标比赛 A 位。
-   来源比赛败者进入目标比赛 B 位。

系统不能只根据比赛编号推测晋级关系。

所有比赛结果和晋级关系必须由后端业务逻辑维护。

# 8. 数据库需求

数据库使用 PostgreSQL。

第一版建议设计以下核心数据表。

  数据表                 用途
  ---------------------- --------------------
  admins                 管理员账号
  competitions           赛事基本信息
  teams                  队伍信息
  players                选手信息
  registrations          报名记录
  registration_members   报名队员及名单快照
  stages                 赛事阶段
  groups                 小组
  stage_entries          阶段参赛队伍
  matches                比赛记录
  match_maps             地图比分
  match_advancements     晋级关系
  live_streams           直播信息
  announcements          公告
  audit_logs             管理员操作记录

## 8.1 核心关系

-   一个赛事有多条报名记录。
-   一支队伍可以参加多届赛事。
-   一条报名记录对应一支队伍。
-   一条报名记录有多个参赛队员。
-   一个赛事包含多个比赛阶段。
-   一个阶段可以包含多个小组。
-   一个阶段包含多支参赛队伍。
-   一个阶段包含多场比赛。
-   一场比赛包含多张地图记录。
-   比赛之间通过晋级关系连接。
-   一个赛事可以配置多个直播入口和公告。

## 8.2 数据设计约束

1.  队伍、赛事和报名记录分开存储。
2.  报名名单保存当届赛事的成员快照。
3.  Steam ID 在同一届赛事中不得重复报名。
4.  比赛胜负由后端计算。
5.  积分榜由比赛结果计算，不直接由前端修改。
6.  管理员操作保留审计记录。
7.  数据库使用外键、唯一约束和事务保证数据一致性。
8.  重要业务数据不全部存入 JSONB。

## 8.3 赛制配置存储

`stages.config` 使用 PostgreSQL JSONB 保存动态规则。

例如：

``` json
{
  "groups_count": 8,
  "teams_per_group": 4,
  "advance_per_group": 2,
  "group_format": "round_robin",
  "best_of": 1,
  "points": {
    "win": 3,
    "draw": 0,
    "loss": 0
  },
  "tiebreakers": [
    "points",
    "head_to_head",
    "map_difference",
    "round_difference"
  ]
}
```

具体配置由后端进行数据验证。

# 10. 非功能需求

## 10.1 性能需求

目标规模：

-   16～32 支参赛队伍。
-   约 100 人同时访问。
-   主要以查询和静态内容浏览为主。
-   视频播放由 B 站承担。

建议进行以下压力测试：

-   100 个并发访问用户。
-   持续测试 10 分钟以上。
-   模拟首页、赛事列表、队伍详情、赛程和比赛详情查询。
-   统计响应时间、错误率、CPU 和内存使用。

建议验收目标：

-   普通公开 API 的 P95 响应时间不超过 2 秒。
-   压测期间 HTTP 5xx 错误率低于 1%。
-   不发生服务器 OOM 或数据库异常退出。

以上为测试目标，不代表 2 核 2GB 服务器已经保证能够达到。

如果不达标，应先优化静态资源、数据库查询和缓存策略，再考虑升级至 2 核
4GB。

## 10.2 可用性

-   网站在比赛期间应保持稳定访问。
-   比赛重要节点前进行数据库备份。
-   重要接口出现异常时返回明确错误信息。
-   管理后台与公开页面相互隔离。
-   提供直播间外部跳转作为备用方案。

## 10.3 安全性

-   管理员密码使用 Argon2 等安全哈希算法。
-   管理后台强制 HTTPS。
-   管理员会话使用安全 Cookie。
-   限制登录尝试频率。
-   对报名接口进行限流。
-   防止 SQL 注入和 XSS。
-   文件上传限制类型、大小。
-   数据库端口不暴露公网。
-   `.env` 等敏感配置不得提交 GitHub。
-   重要管理操作记录日志。

## 10.4 隐私保护

公开展示：

-   队伍名称。
-   队伍 Logo。
-   游戏昵称。
-   比赛成绩。
-   公开介绍。

默认不公开：

-   手机号码。
-   邮箱。
-   私人联系方式。
-   其他非必要个人信息。

Steam ID 作为管理和重复报名校验信息，默认不公开。

个人信息收集应遵循必要、明确和最小化原则。

## 12.1 预算目标

## 12.2 成本估算

按照截图中经济型 e 的 0.123 元/小时参考价格：

90 天的原始计算费用约为：

0.123 × 24 × 90 = 265.68 元。

但截图中的试用有效期、免费额度和可用时长并不相同，不能简单认定整个 90

# 14. 风险及待确认事项

以下事项不影响当前技术架构设计，但需要在正式开发或上线前确认。

  编号   待确认事项                       影响
  ------ -------------------------------- --------------
  Q01    报名是否仅限校内学生             报名资格验证
  Q02    是否采用邀请码报名               报名系统
  Q03    分组采用随机、手动还是种子混合   赛程系统
  Q04    是否举办季军赛                   淘汰赛
  Q05    小组赛是否采用单循环             赛制配置
  Q06    是否允许比赛特殊平局             积分规则
  Q07    最终地图池和比赛规则             比赛记录
  Q08    是否公开选手 Steam ID            隐私与展示
  Q09    是否支持比赛 Demo 或视频回放     比赛详情
  Q10    B站直播间是否允许网站嵌入        直播模块
  Q11    学校能否提供备案域名             正式上线
  Q12    试用结束后的服务器费用           项目预算
  Q13    是否支持未来其他电竞项目         后续扩展

## 14.1 主要风险

**服务器风险**

2GB 内存可能受到 PostgreSQL、FastAPI 和 Nginx
同时运行的资源限制，需要压测，必要时升级到 4GB。

**网络风险**

服务器带宽、图片传输和校园网络质量可能影响访问体验。应压缩图片，缓存静态资源，并在比赛前进行真实网络测试。

**赛制风险**

双败淘汰和非 2
的幂次方队伍数量会增加赛程生成复杂度，需要使用测试数据验证。

**数据风险**

错误修改比分可能影响后续晋级，需要事务处理、操作日志和结果修正机制。

**合规风险**

试用 ECS 不满足 ICP 备案要求，正式公开部署前需要确认合规资源。

**直播风险**

B站播放器嵌入的可用性需要提前验证，同时保留直接跳转直播间的备用入口。

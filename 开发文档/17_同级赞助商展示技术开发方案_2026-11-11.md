# 同级赞助商展示技术开发方案

日期 2026-11-11（Asia/Shanghai） · 版本 V1.0 · 样式已确认，功能已实现，正式品牌待录入

## 1. 交付范围

调整公开「最终排名」页 `/results`、按届结果页 `/results/:slug` 的合作伙伴区，并同步后台结果预览与离线 HTML 导出。当前赛事展示两家同级赞助商。后台可继续为本届关联品牌、调整顺序和控制公开状态。公开页面随新版本发布更新。

现有页面按「首席赞助商」和「合作伙伴」分区。公开结果的数据结构、发布校验、奖品署名和合作详情都依赖单个 `presenting_partner`，所以本次需要同步修改前后端。冠军纪念章、最终名次、奖品数量与分配、比赛详情继续走现有逻辑。

本方案沿用 [最终排名 V6 交付记录](13_最终排名V6开发交付与验证.md) 和 [示例数据后端化交付记录](16_示例数据后端化开发交付与验证_2026-11-10.md) 中的排名发布流程。独立预览中的 NEXCORE、FRAME、LINKUP、REPLAY 是用于校对版式的示例标识。两家正式品牌的名称、Logo、顺序及实际奖品归属以组织方提供的资料为准。

## 2. 已确认样式

| 项目 | 实现规格 |
| --- | --- |
| 标题 | 左对齐。上方为荧光黄 `OFFICIAL PARTNERS` 与短斜纹，下方为粗体「合作伙伴」。字号从窄屏约 30 px 到桌面约 54 px。 |
| 底色与纹理 | 区块底色 `#101011`，Logo 共用一整条近黑底带，带有低对比度斜向暗纹。荧光黄 `#e3fa3e` 用于标题标识、底带顶部短线和分隔线中段。 |
| 布局 | 桌面每行两列等宽。每行高度随屏宽变化，约 106–178 px。首行两家并排，第三家进入下一行左侧，第四家补齐右侧，后续依次换行。空位延续底带背景。 |
| 分隔 | 双列之间用短斜线，居中占单行高度约三分之二。行与行之间用细水平线。510 px 及以下改为单列，使用水平分隔。 |
| Logo | 每家一个居中的 Logo 展示位，统一视觉面积。宽版、方形、竖版图片等比缩放，用 `object-fit: contain`。预览为浅色示例标识，实际图片使用品牌提供的深底适配版本并保留原色。缺图或加载失败时用品牌名兜底。 |
| 动效 | 赞助区首次进入视口时，Logo 由斜向遮罩展开并轻微横移，单次约 560 ms，相邻 Logo 间隔 65 ms，每行重新起算。桌面悬停时 Logo 上移约 3 px、放大至约 1.035 倍，底部柔光在约 280 ms 内显现。触屏默认显示完整 Logo。尊重 `prefers-reduced-motion`，减弱动效时直接显示完整内容。 |

正式页面只展示发布数据。预览里的数量切换和「重播入场」属于评审控件。合作详情有资料时可从对应 Logo 打开，复用现有弹窗与键盘焦点返回。没有详情的 Logo 作为静态标识显示。

## 3. 后端开发

### 3.1 复用品牌库与赛事合作关系

- `Sponsor` 保存品牌名、英文名、Logo、介绍、官网和启用状态。品牌可跨届复用。Logo 沿用 `POST /api/v1/admin/assets`，接受 PNG、JPEG、WebP，大小上限 2 MiB，最长边上限 4096 px，后端转 WebP 并返回站内媒体地址。
- `CompetitionPartner` 保存品牌与赛事的关联、排序、公开状态及本届合作说明。同一品牌在同届唯一。继续使用关联记录的 ID 作为 `Prize.provider_partner_id`，奖品提供方校验按赛事关联执行。
- 新增合作关系时统一使用 `tier=official`。保留已有 `presenting` 记录及接口兼容值，发布新版时两种旧值均可进入同级列表。后台修改既有合作关系时保存原值，实际奖品提供方变更通过原奖品编辑入口处理。
- 本次使用已有字段和 JSON 快照，数据库结构继续采用迁移 004。已有合作、品牌和历史快照无需批量改写。

实现入口见 [数据模型](../backend/app/db.py)、[品牌与合作管理](../backend/app/final_results.py)、[媒体上传](../backend/app/content.py)。

### 3.2 统一公开数据

在 `final_results.preview()` 生成的结果对象中增量加入 `partners`。工作稿预览和新发布快照复用这份生成逻辑。列表仅收录本届 `published=true` 且品牌 `active=true` 的记录。先按 `display_order` 升序，再按关联 ID 排序。缺省顺序按 0 处理，保存时规范为整数。

```json
{
  "partners": [
    {
      "id": "competition-partner-id",
      "name": "品牌名",
      "english_name": "Brand",
      "logo_url": "/media/brand.webp",
      "display_order": 10,
      "category": "赛事外设支持",
      "introduction": "品牌介绍",
      "support_description": "本届合作内容",
      "official_url": "https://example.com"
    }
  ]
}
```

按字段白名单构造新增列表。名称和关联 ID 必有，排序有默认值，其余展示字段可空。历史内置标识如 `builtin_mark_key` 仅用于已有示例品牌兼容。官网地址继续用现有 HTTPS 校验。

新快照继续返回旧 `presenting_partner` 和 `official_partners` 作为过渡兼容字段，沿用其原含义。前端优先使用 `partners`，显式的空数组就是本届没有公开合作。仅在该字段缺失时，从旧快照的两个字段合并、去重并排序。读取 `/api/v1/results/latest` 与 `/api/v1/competitions/{key}/results` 继续直接返回已发布快照。历史快照的合作名单、Logo、版本和校验值都以原发布记录为准。

### 3.3 校验、发布与奖品关联

1. 保留冠军、名次、赛果、分配数量及正式／测试排名的原有校验。将「缺少冠军或已公开首席赞助商」拆为冠军校验，去掉首席赞助门槛。两家均为 `official` 时可完成发布。
2. 从统一 `partners` 列表构建公开合作 ID 集合。对已有分配的奖品，若奖品已停用、提供方未公开或品牌已停用，继续阻止发布。错误提示指出需恢复公开或改到本届真实提供方。
3. 沿用 `expected_version`、源指纹、行锁、幂等键和发布审计。品牌 Logo、排序、启用及公开状态已包含在源资料中，保存后需重新校验最新稿。发布成功时将完整列表写入新的 `ResultRelease.public_snapshot`，再切换本届当前发布版本。

奖品区标题列出实际提供已分配外设的品牌。切换获奖名次时，主产品署名取该产品的 `provider_partner_id`，完整名次表按实际分配的奖品汇总并去重提供方。纪念品和外设数量继续从 `support_totals` 读取，在奖品区展示。

## 4. 前端与管理后台开发

| 实现入口 | 改动 |
| --- | --- |
| [结果页模板与渲染](../frontend/src/results/render.ts) | 在 `ResultDTO` 中增加类型化的可选 `partners`，集中处理新旧数据兼容并按 ID 建立查询。API 公开、后台预览和离线模式渲染同一合作伙伴区块，复用现有 `#partners`。有公开品牌时按数据生成 Logo 行，空列表时隐藏整个区块。 |
| [结果页交互](../frontend/src/Results.vue) | 合作详情使用关联 ID 查找品牌，按各自资料生成弹窗。动画复用现有可视区域监听，奖项切换、后台预览刷新和公开页同版本轮询时避免重播已显示的赞助区。 |
| [结果页样式](../frontend/src/results/partners.css) | 冻结 demo 使用 V6 模板和原视觉基线。新样式按独立赞助区选择器限定作用范围，使用现有本地字体资源，同时纳入在线与离线样式入口。 |
| [离线导出](../frontend/src/results/offline.ts) | 复用统一的赞助区模板和按 ID 构建的详情，继续将 `/media/` 图片打包进文件。断网打开时 Logo、文字和奖品署名可见。旧 demo 的详情触发路径保留。 |
| [后台表单](../frontend/src/FinalResultsAdmin.vue) | 复用品牌库和本届合作接口。合作区显示 Logo 缩略图、品牌名、展示顺序及公开状态。新增表单默认未公开，提交后可编辑排序或公开状态。日常界面移除首席选择，新关联发送 `official`。品牌编辑处继续保留图片预览。 |

后台操作顺序为「选择赛事 → 最终排名与奖励 → 保存品牌与 Logo → 添加本届合作 → 设置顺序并勾选公开 → 内部预览 → 校验 → 填写原因并发布」。排序建议按 10、20、30 录入，便于后续插入。多届共用品牌时，用本届合作状态控制单届展示。全局品牌停用影响使用该品牌的后续发布。

## 5. 当前赛事资料更新与上线

1. 先备份数据库和媒体，记录现有公开版本、示例合作状态和各奖品的原提供方。发布端先部署兼容新旧快照的前端，再更新后端，之后录入正式品牌资料。
2. 收齐两家正式 Logo、品牌名、展示顺序和奖品归属。在当前赛事后台添加两条同级合作，核对预览。逐项将实际由新品牌提供的奖品指向对应合作 ID，再取消本届旧示例合作的公开状态。保留示例品牌与旧版媒体，以供已有快照读取。
3. 确认本届预览只有两家真实品牌、奖品署名准确、数量符合现有分配，再发布结果新版。分别检查 `/results` 与本届按路径访问的页面，确认读到目标赛事版本。
4. 样式有问题时回退前端构建。已经发布只有同级赞助商的新版时，保留能读取该数据的前端。资料错误时按记录恢复该届工作稿、预览校验后重发更正版本。

## 6. 验收

- 后端覆盖两家同级、同排序时顺序稳定、未公开或停用记录过滤、奖品提供方校验、新旧快照兼容，以及正式／测试排名发布流程。验证后台保存后公开版本仍读取已发布数据，新版发布后仅更新本届当前版本。
- 浏览器覆盖 2、3、4 家及更多赞助商、510/511 px 断点、320 px 窄屏、横竖 Logo 和缺图兜底。对照确认的斜切样式验收入场、悬停、减弱动效及滚动回到区块的表现。
- 使用真实 API 验收上传 Logo、关联赛事、排序、公开、预览、发布的完整流程。逐一核对奖品区、名次表、合作详情及断网导出。跑既有正式排名、测试数据和冻结 demo 视觉回归。

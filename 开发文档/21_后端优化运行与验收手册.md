# GDUF CS 后端优化运行与验收手册

本文对应 20 号方案和 Alembic 008。生产发布前先从实际服务器核对应用镜像、数据库 revision、代理拓扑和备份编号。仓库内历史发布记录仅用于追溯。开发时记录的原工作区哈希见 `reports/backend-quality-baseline.json`。

## 事务与兼容

- HTTP 函数作用域依赖和 CLI 调用方拥有写事务。服务接收一个 Session。涉及多个赛事时，先按 ID 锁赛事，再锁结果页，最后按实体类别和 ID 顺序取锁。示例数据导入另先锁唯一管理员协调行。进入赛事锁之后重新读取实体。请求处理成功且事务提交后，才尝试刷新 Redis。
- 名单、成绩、晋级、赛程和排名发布规则集中在 `backend/app/services`。名单绑定发生在参赛方确定时。比赛按历史版本显示。出现无证据的旧记录时，006／008 迁移报告对应对象并要求核对。奖品计划属于服务器，编辑工作稿时保留，展示设置按子字段合并。
- 当前版本的后台在会改变比赛状态、阶段、赛事设置、公告和直播的操作里传递 `expected_version`。原先无版本字段的 v1 请求仍可提交以兼容现有调用方，升级客户端后才能获得这些接口的过期写保护。成绩和排名等已有版本必填的接口继续强制检查。
- 确认、发布、导入等关键命令可以使用操作键。同操作键同输入重放事务保存的首个结果。不同输入返回 409。Excel 提交后保留摘要，预览资料有 30 分钟窗口。赛事凭据随赛事保留。历史记录不补造操作回执。
- 通用列表原数组入口保留。赛事、公告增加 `/api/v1/pages/...`，审计分页使用 `/api/v1/admin/audit-logs/page`，后台审计已切换。新增列表客户端可按需分页；OpenAPI 在 `reports/backend-quality-openapi.json`。

## Redis 与故障操作

Compose 固定 Redis 8.10.3 镜像摘要。Python 客户端锁定 redis-py 8.1.0。Redis 走内部网络，生产 .env 配置独立随机的 `REDIS_PASSWORD`、`LOGIN_SOURCE_SECRET`、`REDIS_NAMESPACE`。用户名为 gduf，凭据和源地址不写入应用日志。

- 缓存只存公开 DTO。128 个固定槽位、每条 256 KiB 上限，业务载荷上界 32 MiB。值和短租约均自动过期。键包含部署命名空间，值带随机代次及参数摘要。
- 公共缓存 TTL 按数据库回源开始前计时，2 秒。Nginx 请求回源并发初始每 API 进程 4。正式排名、管理接口、HTML 存在检查直接访问数据库。
- `cache-outbox` 从 PostgreSQL 读取待失效事件。服务重启后自动重放。通过内部 `/internal/components` 查看 `recovering`、`login_protected`、`ready`。缓存未就绪或 Redis 不可用时，游客读有界回源。新登录返回 503，现有会话继续使用。
- Redis 实例 ID 变化或控制状态丢失时，worker 切换缓存代次并重放事件。启动或恢复时新登录保护不少于 5 分钟。Redis 使用 noeviction 与 AOF everysec。恢复 PostgreSQL 后使用新的 Redis 命名空间，先启动 worker，观察积压处理，再开放流量。
- 应用单进程数据库池 5 个连接，worker 2 个。启动双 API 进程时分别计算连接、同步回源、Redis 连接及 Argon2 内存。Redis 初始 maxmemory 128 MiB，容器限额 256 MiB，生产值依据峰值和 AOF 重写实测校准。

## 发布与恢复

1. 在版本库固定发布提交，构建并保留 API 和 Web 镜像，记录摘要。API、迁移、worker 使用同一 API 镜像。在发布环境预拉受控镜像，设置 `API_IMAGE`、`WEB_IMAGE`，记录配置的摘要及备份编号。相同部署目录依次执行，避免两个迁移实例同时运行。
2. 计划写入维护窗口。先备份并核对校验和，在隔离副本预演 `alembic upgrade head`。006／008 有存量核对，跨届、胜者与名单版本问题按对象核实。通过后执行唯一的 migrate 服务，确认 revision 008 和 API 就绪，再切换流量。008 后旧应用创建晋级关系的字段不兼容，回退需要独立恢复备份并核对备份之后新增的数据。
3. `bash scripts/backup.sh <新目录> consistent` 停止 API 写入后制作数据库和媒体备份，完成时恢复 API。在线模式有数据库与媒体一致性窗口。计划外或失败可从日志核对服务启动状态。 `deploy/ops` 已提供 systemd 服务、定时器和告警规则；定时使用北京时间 04:30。
4. 异地版 `scripts/backup-offsite.sh` 依赖 age、rclone 和受控配置。设置 `GDUF_BACKUP_ROOT`（权限 0700）、`GDUF_BACKUP_REMOTE`、`GDUF_BACKUP_AGE_RECIPIENTS`、`GDUF_BACKUP_METRICS_DIR`。异地日、周、月前缀分别配置 7 天、28 天、90 天生命周期，并以符合部署容量的方式清理本地已验证备份。配置、证书、解密密钥独立保管。备份包上传后重新读取校验，再更新最近成功指标。
5. 在独立 Compose 项目先启动空 PostgreSQL 和空媒体卷，准备当次镜像。执行 `bash scripts/restore.sh <备份目录> EMPTY_DATABASE_ONLY`。脚本核对源校验和并拒绝已有数据的目标库或媒体卷。完成后核对名单与发布快照摘要、表计数和媒体哈希，使用不同 Redis namespace 启动并抽查公开页面。从开始恢复到就绪的实际耗时单独记入验收。
6. `/health/live`、`/health/ready`、`/internal/components`、`/internal/metrics` 从受控网络访问；公网代理继续暴露现有 `/api/v1/health`。监控采集内部 API 指标和主机磁盘指标，导入 `deploy/ops/alerts.yml` 并配置告警接收渠道。

## 隔离验收

- 常规后端测试在 `backend` 执行 `python -m pytest tests -q`。Windows 采用权限正常的短临时路径（如 `--basetemp storage/q-local`），配合 `-o faulthandler_timeout=25`。真实 PostgreSQL 回归必须设置 `GDUF_TEST_ISOLATED=1` 并面向本机独立 `gduf_test`，测试按用例重建业务表。
- `tests/test_quality_integration.py` 使用本机隔离 `gduf_quality`、独立 Redis 和两个 API 进程。配置 `DATABASE_URL`、`QUALITY_REDIS_URL`、`QUALITY_REDIS_CONTAINER`，后者用于在测试中重启已确认隔离的 Redis 实例。CI 运行同一验证。
- 性能数据用空的本机 `gduf_perf`：先迁移，再在 `GDUF_TEST_ISOLATED=1` 下执行 `python -m app.jobs.seed_quality`。固定到达率脚本 `scripts/quality-load.js` 支持 hot、uncached、mixed、steady。使用独立负载机，通过测试 Nginx 入口运行。uncached 同时配置 API `PUBLIC_CACHE_DISABLED=1`。mixed 使用专用合成管理员和脚本打印的公告 ID。记录每种配置的耗时、真实请求吞吐、失败和资源曲线。
- 新装尝试无法通过 Redis 权限或登录一直受阻时，检查 worker 日志、内部组件状态及 ACL 设置。先检查运行状态和数据库积压，再进行重启排查。已有 PostgreSQL 业务数据优先保护，不以清空 Redis 代替恢复步骤。

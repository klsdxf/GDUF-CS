# 实时访问统计技术开发方案

日期 2026-11-18（Asia/Shanghai） · 版本 V1.2 · 已并入服务器发布候选

## 1. 交付范围

在广金主场管理后台新增「访问统计」，显示全站实时在线人数、今日独立访客（UV）、今日浏览量（PV）以及近 7 天和近 30 天的每日趋势。前台在公开页面成功显示后上报浏览，并在页面可见期间发送心跳。统计从正式启用当天开始积累，仅由管理员查看。

沿用 Vue 3、FastAPI、SQLAlchemy、Alembic 和 PostgreSQL。访问统计的采集、查询和历史存储均走 PostgreSQL，无需新增常驻服务。独立访问统计分支的迁移 `visit_stats_001` 与后端工程优化的 `008` 在本发布分支汇合为 `009`。已有版本通过 `alembic upgrade head` 汇合。参见 [合并迁移](../backend/migrations/versions/009_release_merge.py)。

## 2. 统计口径

| 指标 | 计算规则 |
| --- | --- |
| 实时在线人数 | 以服务端时间为准，对最近 60 秒内成功上报浏览或心跳的浏览器标识去重。页面可见时每 30 秒发一次心跳，重新可见时立即补报。关闭、隐藏或断网后，距最后一次成功上报满 60 秒即退出在线统计。 |
| 今日 UV | 按北京时间 `00:00` 切日。同一浏览器当天首次成功上报浏览或心跳时计 1，之后保持为 1。页面跨零点持续可见时，零点后的首次心跳计入新一天的 UV。 |
| 今日 PV | 公开页面成功展示一次计 1，包括首次打开、手动刷新、切换到另一条公开页面路径。心跳、自动更新、只改变筛选参数或锚点，以及同一页面局部交互均不计入。 |
| 近 7 天／30 天 | 包含今天，以北京时间自然日划分，按日期由早到晚列出每日 UV、PV，并汇总该时段的 PV。每日 UV 单独展示，首版不提供整个时段的去重 UV。当天数据持续更新。 |

统计以当前站点下的浏览器存储为单位。同一浏览器的多个标签页共用一个标识，无痕窗口、清除站点数据、换浏览器或设备可能生成新标识。实时卡片副标题使用「最近 60 秒活跃浏览器」，让管理员能按这一口径解读人数。

## 3. 前台采集

### 3.1 采集时机

| 入口 | 接入方式 |
| --- | --- |
| [公开页面容器](../frontend/src/Public.vue) | 挂载一套全站公开页采集逻辑。普通路由在当前请求确认成功且实际内容渲染后触发 `page_view`。拥有独立公开路径的详情弹窗，在该路径对应的内容成功展示后计入。 |
| [最终排名](../frontend/src/Results.vue) | 最终排名由独立组件加载。由子组件在公开内容成功显示后通知页面容器，包含正常展示的待发布状态。自动刷新和后台预览走各自流程，不触发浏览事件。 |
| 页面可见状态 | 首次成功展示且可见时发送 `page_view`，它同时刷新在线时间。初次在后台标签加载时延后到首次可见。切回已计数的页面只发 `heartbeat`，每 30 秒继续发一次。页面隐藏、进入错误页或离开公开页时停止定时器，卸载时清除计时器和监听。 |

以当前导航的规范化路径和请求序号配对，拒绝沿用上一页数据的迟到回包。一次导航只上报一次，浏览器刷新或再次进入该页面会开启新的一次导航。像 `/results?edition=…` 这样的历史跳转只统计最终落地页。后台、开发预览、demo 模式、离线导出的排名、404 和加载失败页均排除；其他数据轮询继续负责更新内容。

### 3.2 浏览器标识与上报行为

- 首次采集生成 UUID v4，使用同源 IndexedDB 的单个读写事务读取或初始化标识，让并发打开的标签页使用同一值。标识供本站统计使用。浏览器存储被禁用或初始化失败时，跳过该次采集，正常显示页面。
- 报文只发送 `visitor_id` 与 `kind`，不发送路径、查询串、来源网址或浏览器指纹。统计按全站汇总，页面是否符合采集条件由前台公开页逻辑判断。
- 上报独立于业务加载，失败时不弹窗、不阻塞导航。每次浏览事件只发送一次，超时或失败不自动重放，后续正常心跳可恢复在线状态。每个标签页最多保留一个心跳请求在途，多个标签页由服务端按标识去重。

## 4. 后端与持久化

### 4.1 接口约定

| 接口 | 输入与输出 | 权限 |
| --- | --- | --- |
| `POST /api/v1/visits` | JSON 请求含 `visitor_id`（UUID v4）和 `kind`（`page_view` 或 `heartbeat`）。成功返回 `200` 和 `{"data":null}`，兼容现有前端 API 封装。 | 公开页同源请求。校验 `Origin` 等于 `PUBLIC_ORIGIN`，限制请求体大小并校验字段。入口限流使用独立配置，避免统计请求占用赛事接口额度。 |
| `GET /api/v1/admin/visits/summary?days=7` | `days` 取 `7` 或 `30`，默认 `7`。响应复用 `data` 包装。返回 `tracking_started_on`、`as_of`、`online`、`today`、`total_pv`、`daily`。 | 复用现有管理员会话鉴权，未登录返回 `401`。 |

`as_of` 为服务端以 UTC 表示的快照时间，`today` 和 `daily` 每项使用 `date`、`uv`、`pv`，其中 `date` 是北京时间的 `YYYY-MM-DD`。启用后没有记录的日期填 0，早于启用日的日期返回 `uv: null`、`pv: null`。`total_pv` 只累计有采集范围的日期。未启用时，收集接口以 `200` 返回空结果且不写数据，汇总接口返回 `tracking_started_on: null` 及空指标，后台相应显示「统计未启用」。统计接口响应设置 `Cache-Control: no-store`。暂不可用时沿用项目错误响应格式，返回适当的错误状态。

公开写入入口接受小型 JSON，建议请求体上限 1 KiB，并拒绝非同源与非法枚举、非法标识。按现有代理拓扑在公网入口单独配置采集限流，联调时验证共享出口下正常访问可以记录。统计只给出可观测浏览器的估计量，自动化访问或浏览器拦截可能造成偏差。管理员读接口继续用现有 [会话鉴权](../backend/app/security.py) 与 [前端 API 封装](../frontend/src/api.ts)。

### 4.2 数据模型

| 表 | 字段及索引 | 用途 |
| --- | --- | --- |
| `visit_visitor_days` | `stat_date`、`visitor_digest`、`last_seen_at`。主键为 `(stat_date, visitor_digest)`，为 `last_seen_at` 建索引。 | `visitor_digest` 由规范化后的随机 UUID 计算 SHA-256，保持跨日可比。表中记录只用于当日去重和在线查询。UTC 时间列使用可表示时区的类型。 |
| `visit_daily_totals` | `stat_date` 为主键，`uv`、`pv` 为非负 64 位整数，初始值均为 0。 | 按北京时间保存每日汇总，纳入现有 PostgreSQL 备份。历史趋势直接查询此表。 |

访问统计表只保存随机浏览器标识的摘要、日期、最后活跃时间和汇总值。短期表保留今天及前两个北京时间自然日，由定时维护删除更早记录。历史汇总表长期保存。应用沿用现有请求错误编号，统计错误记录不包含上报标识或完整请求体。

### 4.3 写入、并发与读取

1. 每个接受的事件使用一次服务端时间，保存 UTC 时间，并用 `Asia/Shanghai` 派生统计日期。先按 `(stat_date, visitor_digest)` 原子插入短期记录，由插入结果判定当天是否首次访问。已有记录更新 `last_seen_at`，取旧时间与事件时间中较晚者，避免并发处理使在线时间倒退。
2. 在同一事务内，仅首次记录增加 `uv`，每个 `page_view` 增加 `pv`。对日期行执行原子累加，普通重复心跳只更新时间，不更新汇总行。事务失败时，两张表一起回滚。保留 PostgreSQL 的并发约束，并验证本地 SQLite 开发路径可运行。
3. 在线查询在最近 60 秒内按 `visitor_digest` 去重，范围跨北京时间零点。同一标识即便当天和前一天都有活跃记录，在线只算 1。历史汇总按日期主键读取最多 30 行，统计响应的时间与日期窗口取自同一次服务端快照。

每个持续可见的标签页每分钟约产生两次心跳，另有导航产生的浏览请求。预发布用预计比赛峰值验证统计写入、在线查询以及对赛程和排名读取延迟的影响，按实测调整入口限流。公网 TLS 入口默认按连接来源限制采集请求为每秒 20 次，允许突发 120 次；正式域名按 `PUBLIC_ORIGIN` 校验。主要接入点是 [统计路由与事务](../backend/app/visits.py)、[增量迁移](../backend/migrations/versions/visit_stats_001.py) 和 [定时清理](../deploy/ops/gduf-visits-cleanup.timer)。

## 5. 管理后台

在 [后台导航](../frontend/src/Admin.vue) 增加「访问统计」，沿用现有单管理员导航和组件样式。第一行放「实时在线」「今日访客」「今日浏览量」三张卡片。下方提供近 7 天和近 30 天切换，展示每日 UV、PV 折线、可直接读取数值的日期明细及所选区间总浏览量。「今日」按北京时间显示，在线卡片标注最近成功更新时间。

进入页面立即请求汇总；可见时每 10 秒刷新，切回标签页时立即刷新，离开统计页或切到后台标签时停止轮询。切换区间时立即查询并避免旧区间的响应覆盖当前结果。单次请求失败时显示「统计暂不可用」，已有快照标为「上次成功数据」，首次失败时保留空白占位。成功读到的 0 正常显示。早于采集开始日的趋势留空，列表显示「未开始采集」。

## 6. 实施与上线顺序

1. 确认生产镜像对应的数据库 revision。在独立副本中验证现网数据能升级至 `009`，再切换生产版本。
2. 完成增量迁移、统计路由、事务和清理，再接入前台采集及后台展示。增加 `VISIT_STATS_START_DATE` 配置，以北京时间日期控制启用。空值表示停用，正式启用时填写当天日期；恢复采集时沿用首次启用日期。演示环境和一般开发环境默认留空，验收使用隔离环境及专用数据库。
3. 功能闭环后集中审查、测试和修正，按下一节验收。以预发布环境的独立数据验证上线、停用和重新启用流程。
4. 发布时先备份并执行迁移，再更新 API 和 Web。用当前域名与证书配置重新生成并校验 Nginx 入口配置，再设置启用日期并重建 API 容器。沿用部署环境的定时维护入口运行 `docker compose exec -T api python -m app.visits_cleanup`，或安装仓库内的清理服务和定时器，核对服务的工作目录后启用 `gduf-visits-cleanup.timer`。需要暂停时清空启用日期并重建 API 容器，已有汇总留存。若停用期间跨天，运营记录需注明缺失时段，历史访问不会补录。回退应用时可保留统计表，执行迁移降级会删除表及统计数据。

## 7. 集中验收清单

| 场景 | 预期结果 |
| --- | --- |
| 两个浏览器同时打开首页 | 在线为 2，今日 UV 为 2，每个浏览器首次打开各计 1 PV。后台在下一轮成功查询后显示结果。 |
| 同一浏览器并行打开多个标签和手动刷新 | 当天 UV 与在线均只计 1，实际成功展示的每次导航分别计 PV。并发首次访问只增加一次 UV。 |
| 页面可见、关闭、隐藏与恢复 | 页面持续可见时心跳只维持在线；距最后成功上报满 60 秒退出统计。恢复可见立即恢复在线，当前页面无新导航时 PV 不增加。 |
| 公开详情、排名与自动更新 | 普通公开页与排名页均可采集。带独立公开路径的详情成功展示计 PV，自动刷新和仅改筛选条件不加 PV。失败页、demo、离线排名和后台没有访问记录。 |
| 北京时间跨日 | 同一浏览器在两天分别计 UV，零点后的普通心跳不增加新日 PV；60 秒窗口内出现两天的记录，在线仍只计 1。 |
| 并发、失败与清理 | 并行 PV 累加完整；事务中途失败不留下半条统计；短期记录清理后既有历史汇总仍可读取。 |
| 区间与启用状态 | 7 天和 30 天均包含今天，日序正确；启用前显示未采集，启用后零流量日显示 0，区间总 PV 等于每日 PV 之和。 |
| 权限、故障与发布回归 | 未登录不能查汇总，非同源和无效上报被拒绝。统计故障不阻塞前台，后台有正确的错误状态。迁移、管理员登录、公开赛程、排名及现有备份恢复流程通过回归。 |

- 后端回归 64 项通过，1 项按既有条件跳过。独立 PostgreSQL 16 验证并发 PV 累加、同一浏览器 UV 去重、事务回滚，以及 `006 → visit_stats_001 → 006 → visit_stats_001` 迁移路径。
- Playwright 28 项通过，覆盖访问统计、API 公开页、赛程及最终排名。前端 CSS 检查、类型检查和生产构建通过。域名与 IP 两套 Nginx 配置在隔离容器通过语法校验。
- 使用两个独立浏览器上下文打开三个公开页面，其中两个页面共用一个浏览器上下文。真实 API 和后台都显示在线 2、今日 UV 2、PV 3。近 30 天汇总返回 30 个自然日与总 PV 3。PostgreSQL 备份恢复到另一空库后，已采集日的 UV 和 PV 仍为 2 和 3。

## 2. 集中验证中修复的问题

1. SQLite 读取日期时丢失时区，导致重新编辑公告被“发布时间需带时区”拒绝：新输入统一转 UTC，公开与后台日期序列化明确附加 UTC；比赛安排冲突比较也统一时区。
2. 手机端原 V6 会隐藏海报换行，长队名会在词中断行：仅为 API 传入的多行海报保留配置换行，原冻结参考不变；离线导出使用相同 CSS。
3. Vite 缺少显式环境值时无法可靠裁剪参考模块：统一定义默认 API 编译常量，构建产物确认不再包含 demo-data／sample-data 模块。
4. 历史 003 使用当前 ORM metadata 建表，旧 002 升级时新增来源 FK 的父表可能尚不存在：003 补建被引用的批次父表，004 仍负责所有新增字段和表的兼容补齐；使用真实冻结 003 SQL 另构造 002 场景验证。

## 4. 上线步骤

本轮完成源码交付与 GitHub 推送，不登录生产服务器，不执行生产迁移或导入。

后续部署按既有交接流程：

1. 核对目标提交及现有资料，备份数据库和媒体，保留旧镜像。
2. 更新兼容后端，显式执行 `alembic upgrade head`，确认至 004。
3. 现有管理员登录“测试数据初始化”，核对预览中的冲突、文案及两场补充对局，再确认提交。已有同 slug 赛事不自动覆盖，不删除数据卷解决冲突。
4. 核对后台四队、公告、测试排名和发布记录。秋季赛仍应为进行中。
5. 以 `VITE_PUBLIC_DATA_MODE=api` 重建前端；根环境示例和 Compose 已默认 API，若服务器旧 `.env` 明确设置 demo，需同步更改后重建。
6. 检查首页、赛事、赛程、队伍、公告、`/results`、`/results/autumn`、后台与深层链接；验证保存／发布后的公开变化。
7. 核对正式环境只保留已确认的正式管理员，排除 `review-admin`、`dataset-admin`、`results-admin`、`test-admin` 等本项目验收身份及其会话。不得将本地验收数据库或登录资料复制到生产。若目标库意外含有测试身份，先按单管理员交接流程处理该身份与旧会话，再完成发布；不直接清空管理员表。

发布包隔离已确认：`backend/.dockerignore` 排除 `tests/`、`storage/`、本地数据库与环境文件；验收账号创建脚本及本地独立验收库不进入后端镜像。正常应用启动和测试业务数据初始化均不创建管理员。四队测试业务资料按本轮需求保留，与需要排除的测试登录账号分开处理。

## 5. 使用边界

- 本次测试排名编辑器与计算器支持已交付的四队、两场半决赛／决赛／季军赛场景，其他人数不会伪造排名，须按新场景扩展后使用。系统赛事容量与正式赛制仍保留原 2～32 队能力。
- 既有已发布赛程的名单锁定规则保持；修改已有队伍资料使用有理由的名单修订，不直接覆盖历史版本。改变整体参赛规模需按已有赛程锁定规则规划新赛事／阶段，不能通过初始化包覆盖。
- 原静态积分与六场对局不完全一致，迁移后按已确认四场小组成绩计算；历史春季／往届没有提供名单与成绩，保留赛事目录及空状态。
- 当前只支持内置包首次初始化与同包幂等重试，不做自动覆盖同步，也不为未来假设场景增加泛化导入框架。
- 线上生效依赖后续部署与显式初始化；GitHub 推送成功不等于线上已更新。
